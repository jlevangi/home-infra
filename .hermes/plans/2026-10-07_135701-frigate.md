# Frigate Deployment Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Deploy Frigate through existing ArgoCD GitOps, strictly on performance nodes, initially with one camera.

**Architecture:** One Frigate replica in its own namespace, with Recreate updates and durable configuration/database storage. Separate recordings storage from configuration; use memory-backed volumes for decoded frames and temporary segments. Require performance-tier scheduling and, when accelerated, the actual compatible device resource as well.

**Tech Stack:** Existing k3s-prod, ArgoCD, Kustomize, Traefik, Longhorn/NFS, official Frigate container.

## Proposed minimum deployment

- Dedicated `frigate` namespace and ArgoCD Application; do not add Frigate to Jellyfin's lifecycle.
- One Deployment replica, Recreate strategy; no autoscaling or second writer to SQLite/recordings.
- Required performance nodeSelector exactly as above. No soft preference or fallback to light nodes.
- If using NVIDIA, also constrain to accelerator-compatible nodes and request the verified device-plugin resource with the existing NVIDIA runtime configuration. Generic performance placement alone does not provide acceleration. If using Intel/another device, require the actual accessible device and compatible node constraint; do not mount nonexistent host devices or use blanket privileged mode by default.
- Pin a tested release tag AND registry digest, with the variant appropriate for the selected backend. Resolve release/schema at implementation time, not `stable`/`latest` alone.
- Start `/config` on a 10Gi longhorn-flash RWO PVC; confirm backup consistency for SQLite. Keep SQLite off NFS. Use ConfigMap plus an init-container copy only if needed to seed an editable config; avoid mounting a read-only ConfigMap over the whole writable /config directory. Declare whether GitOps config or UI editing owns the config before implementation.
- Mount a dedicated NAS directory at `/media/frigate`; do not reuse Tunarr's directories and do not create a Longhorn recording PVC. Verify the selected export/path and write permissions. Configure one-day continuous retention using the selected release's schema; cap review/event retention accordingly. Keep this disposable video outside routine configuration/database backups.
- Memory-backed emptyDir at `/dev/shm` and `/tmp/cache`, each with sizeLimit. Calculate shared memory from detection resolution/count using official formula plus 40MiB logs overhead. Budget both volumes within the pod memory limit; begin cache near 1Gi only after checking the total memory budget.
- Use low-resolution detection substream, initially around 5fps, with native-resolution main stream for recording. Prefer stream copy and built-in go2rtc instead of a separate restreaming service.
- Vault-backed ExternalSecret for camera/MQTT credentials, injected through supported `FRIGATE_*` substitutions. Never commit stream URLs with credentials. Inspect existing SecretStore conventions without dumping secret values.
- Traefik ingress to authenticated port 8971, matching the selected release's HTTP/TLS behavior. Keep port 5000 off ingress and external services; limit internal unauthenticated access to explicitly required integrations/probes/metrics. Verify actual TLS termination and external access boundary before exposure.
- Do not expose 8554 or 8555 initially. Add authenticated RTSP restreaming or LAN-reachable TCP/UDP WebRTC only if needed; verify routing/candidate behavior rather than assuming HTTP ingress handles UDP.
- Startup/readiness/liveness probes using a supported internal health endpoint. Set resource requests/limits from the pilot, including tmpfs usage. Establish read-only monitoring through existing Gatus/Prometheus conventions where available; avoid building a new monitoring stack.

## Implementation sequence and gates

### Task 1: Resolve camera, storage and integration requirements

Record non-secret camera metadata and chosen retention. Identify an existing MQTT broker if Home Assistant is requested. Estimate continuous recording as roughly 10.8 GB/day per 1 Mbps of aggregate bitrate, multiply by retention, then reserve filesystem/free-space headroom. Event-only savings must be measured, not assumed.

### Task 2: Verify hardware access

Inspect node runtime/device-plugin settings, allocated device resources, actual GPU/iGPU model and VM passthrough. Confirm selected backend supports camera codecs and model. Verify host/device permissions with the smallest authorized test; node labels alone are not evidence of inference or decoding.

### Task 3: Verify storage and secret conventions

Read comparable ExternalSecret/SecretStore references without reading resolved secret payloads. Check chosen volume free space, NFS write permissions/throughput, and database backup policy. Preserve existing NAS media. Select exact recordings capacity/path, memory volumes and pod resource budget.

### Task 4: Add minimal manifests

Follow the files above and Tunarr's strict performance selector. Include one camera, one-day continuous NAS recording retention, and the existing Home Assistant MQTT broker with Vault-backed credentials. Validate against the exact selected Frigate release schema. Render:

```bash
kubectl kustomize argocd/manifests/frigate/overlays/prod
kubectl kustomize argocd/manifests/frigate/overlays/prod | kubectl apply --dry-run=client -f -
```

Assert rendered Deployment has one replica, Recreate, the exact performance selector, both memory-backed mounts and the appropriate accelerator request. Check ingress never targets port 5000. Inspect diff for credential leaks and unrelated edits. Use existing validation tools rather than adding a framework.

### Task 5: Approved scoped pilot rollout

Only after implementation review and explicit production-rollout approval, register the named child Application and sync only its root resource if root is manual; never sync unrelated root drift. Verify:

```bash
kubectl --context k3s-prod get application frigate -n argocd
kubectl --context k3s-prod rollout status deployment/frigate -n frigate --timeout=300s
kubectl --context k3s-prod get pods -n frigate -o wide
kubectl --context k3s-prod get pvc -n frigate
```

Require Synced/Healthy, bound storage, one ready replica on an eligible performance/device node. Verify actual detection and decode logs/metrics, not merely startup. Check authenticated HTTPS UI, unauthorized access denial, live view, a recorded segment, event detection and export playback. Ensure unauthenticated API and restream ports are not externally accessible.

### Task 6: Expand after pilot

Observe a representative day of camera reconnects, inference latency, dropped frames, CPU/GPU/memory and storage growth, including activity periods and concurrent Jellyfin/Tunarr usage. Check retention cleanup and safe database restart persistence. Add cameras individually; tune requests, detection resolution/fps and recording capacity using measurements. Test rescheduling only between compatible nodes; hardware failure may intentionally leave Frigate Pending instead of silently falling back to unsuitable nodes.

## Rollback and risks

- Hardware passthrough/backend availability is the principal unverified prerequisite. If no suitable accelerator is exposed to a performance guest, reassess that prerequisite before production detection rollout.
- Recording IO/replication/backups may cost more than compute. Keep bulk media separate from config and avoid inherited full-video backups.
- Memory-backed volumes count against memory consumption; undersizing causes bus errors/OOM, oversizing consumes schedulable capacity.
- One replica has restart downtime; do not promise active-active/high availability for a SQLite NVR.
- Revert deployment/config changes through GitOps while preserving PVCs and media. Database migrations may prevent image downgrade; take a tested consistent config/database backup first. Do not delete the ArgoCD app with cascading finalizers as a routine rollback.
