     Fix personal health dashboard + bring health-archive under GitOps

     Context

     The Grafana "Personal Health" dashboard (argocd/manifests/monitoring-config
     /overlays/prod/personal-health-dashboard.json) shows "You do not currently
     have a default database configured for this data source" on every panel.
     All 8 panels correctly reference a Postgres datasource by uid: 
     health-archive, and their SQL is correct — this was verified directly
     against the live database, which is healthy and actively receiving data
     (steps, heart rate, etc. current through today).

     Root cause: the health-archive Grafana datasource was created by hand
     through the Grafana UI, not provisioned via GitOps. Grafana's "Test" button
     only checks host/auth reachability — it doesn't require a database name —
     so the test passed while the Database field was left blank. Any actual
     query then fails with exactly the error being seen.

     Digging further surfaced a bigger gap: the entire health-archive namespace
     (the health-postgres Deployment, its PVC, and its credentials Secret) was
     deployed straight with kubectl apply, bypassing ArgoCD entirely — the only
     namespace in the cluster like this. Concretely that means: no backups (the
     PVC has none of the recurring-job-group.longhorn.io/* labels every other
     prod PVC has), no reproducibility if the node/PVC is lost, and the DB
     password isn't in Vault. Given the stated goal — a durable, self-owned
     health data store instead of relying on third parties — this is the one
     part of the pipeline that isn't actually durable. This plan both fixes the
     dashboard today and folds the pipeline into the same GitOps/Vault pattern
     already used for every other Postgres-backed app in the repo (closest
     analog: n8n-postgres).

     Confirmed live facts (read-only kubectl inspection, prod cluster):
     - Service: health-postgres.health-archive.svc.cluster.local:5432
     - Database: health_archive, user: health_archive
     - Password: Secret health-postgres-secret (key postgres-password) in ns
     health-archive
     - PVC: health-postgres-pvc, 10Gi, storageClassName: longhorn, no backup 
     labels
     - Data: rich and current (e.g. steps through 2026-08-08, heart_rate through
     2026-08-06) — the n8n/Health Sync ingestion pipeline itself is working
     fine
     - No ArgoCD Application tracks this namespace; it's fully out-of-band

     Phase 1 — Unblock the dashboard today (manual, ~1 minute)

     In Grafana (https://grafana.levangie.dev) → Connections → Data sources →
     find the datasource with UID health-archive → set Database to
     health_archive → Save & Test. Refresh the Personal Health dashboard; panels
     should populate immediately since the data itself is already there and
     correct.

     This step is manual because it requires Grafana admin session/UI access I
     don't have. Phase 2 makes it permanent and removes the need to ever repeat
     this by hand (GitOps provisioning will own/overwrite this same UID going
     forward).

     Phase 2 — Bring health-archive under GitOps

     1. New app manifests: argocd/manifests/health-archive/base/

     Mirror the existing n8n-postgres pattern (argocd/manifests/n8n/base/)
     exactly, sized down to just the DB (no app container needed here):
     - namespace.yaml — namespace health-archive
     - pvc.yaml — same as live (10Gi, storageClassName: longhorn) plus
     recurring-job-group.longhorn.io/daily: "enabled" and .../weekly: "enabled"
     labels (labels are mutable — this patches the existing PVC in place, no
     data loss, hooks it into the existing prod NFS backup job)
     - deployment-postgres.yaml — reproduce the live Deployment spec as-is
     (image postgres:16-alpine, same resources/probes/env —
     POSTGRES_DB/POSTGRES_USER as literal values matching current live config,
     POSTGRES_PASSWORD via secretKeyRef on
     health-postgres-secret/postgres-password, same PVC). Keeping values
     byte-identical to live means this diffs clean with no forced pod restart.
     - service.yaml — ClusterIP health-postgres, port 5432 (matches live)
     - external-secret.yaml — ESO ExternalSecret (pattern:
     argocd/manifests/n8n/base/external-secret.yaml), secretStoreRef: vault-kv,
     target health-postgres-secret, data: [{secretKey: postgres-password, 
     remoteRef: {key: prod/health-archive, property: POSTGRES_PASSWORD}}]
     - kustomization.yaml listing the above

     2. New Application: argocd/apps/prod/health-archive.yaml

     Same shape as argocd/apps/prod/n8n.yaml: path: 
     argocd/manifests/health-archive/base, destination.namespace: 
     health-archive, syncPolicy.automated: {prune: true, selfHeal: true},
     syncOptions: [CreateNamespace=true].

     3. Seed Vault with the existing password (no value ever printed to 
     chat/logs)

     kubectl -n vault-raft exec -it vault-raft-0 -- vault kv put
     kv/prod/health-archive \
       POSTGRES_PASSWORD="$(kubectl -n health-archive get secret
     health-postgres-secret -o jsonpath='{.data.postgres-password}' | base64
     -d)"
     This makes ESO reproduce the exact current password, so the live Postgres
     role and the GitOps-managed Secret stay in sync — no auth breakage, no
     manual password rotation needed.

     4. Provision the Grafana datasource declaratively

     In argocd/apps/prod/kube-prometheus-stack.yaml, under
     grafana.additionalDataSources (next to the existing Loki entry), add:
     - name: Health Archive
       uid: health-archive
       type: postgres
       access: proxy
       url: health-postgres.health-archive.svc.cluster.local:5432
       database: health_archive
       user: health_archive
       jsonData:
         sslmode: disable
         postgresVersion: 1600
       secureJsonData:
         password: $__env{HEALTH_ARCHIVE_DB_PASSWORD}
     And add HEALTH_ARCHIVE_DB_PASSWORD to the existing grafana.envValueFrom
     block (same mechanism already used for
     GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET), sourced from a Secret in the
     monitoring namespace (Grafana can only read secrets in its own namespace).

     That Secret is created by a new ExternalSecret — argocd/manifests/monitorin
     g-config/overlays/prod/external-secret-health-archive.yaml, matching the
     existing external-secret-home-assistant.yaml pattern:
     apiVersion: external-secrets.io/v1
     kind: ExternalSecret
     metadata:
       name: health-archive-db-credentials
       namespace: monitoring
     spec:
       refreshInterval: 1h
       secretStoreRef:
         name: vault-kv
         kind: ClusterSecretStore
       target:
         name: health-archive-db-credentials
         creationPolicy: Owner
       data:
         - secretKey: password
           remoteRef:
             key: prod/health-archive
             property: POSTGRES_PASSWORD
     Add it to
     argocd/manifests/monitoring-config/overlays/prod/kustomization.yaml
     resources list.

     Once ArgoCD syncs kube-prometheus-stack, Grafana's provisioning will own
     the health-archive UID and overwrite whatever was set manually in Phase 1 —
     so Phase 1's manual step becomes permanent/reproducible rather than
     needing to be redone after a Grafana restart.
