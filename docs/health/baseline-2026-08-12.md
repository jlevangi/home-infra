## What the schema actually contains

Five tables, not the three the service code implies:

- `health_observations_raw` — the EAV observation table
- `health_sources`
- `health_ingested_files` — the Google Drive ledger
- `health_daily_summaries` — written by `refresh_health_daily_numeric_summaries`
- `health_daily_source_comparison` — same

Two functions: `text_to_timestamptz_immutable(text)` and
`refresh_health_daily_numeric_summaries(date, date)`.

`refresh_health_daily_numeric_summaries` is **not** orphaned dead code, as the
service source suggests. It is a large plpgsql function that already implements
per-metric source precedence, unit normalisation (mi→m, lb→kg, ft→m, SpO₂
fraction→percent) and per-metric aggregation rules (avg vs last vs sum). Nothing
in the repository calls it any more — the v2 n8n workflow dropped the call — so
the two summary tables are going stale. That function is the closest thing to a
specification of intent for this archive; read it before designing any
replacement.

## Things worth knowing before changing anything

- **`value_numeric` is `real`**, i.e. single precision, ~7 significant digits.
  `db.py` declares `double precision` in `_INGEST_SQL`'s `jsonb_to_recordset`
  and then inserts into a `real` column, so values are silently downcast. Max
  stored value today is 95,807.1 and nothing exceeds 2²⁴, so no integer
  precision has been lost yet — but this is a lossy choice for a permanent
  archive.
- **`health_observations_raw.id` is `integer`**, not `bigint`. 4.5M of 2.1B used.
- **There is a `person_id text DEFAULT 'pierce'` column** on the observation and
  summary tables. Nothing in the service code sets it; it relies on the default.
- `start_time`/`end_time` are `text`. The three indexes are
  `idx_health_raw_metric_type_start_time_ts` (functional, via
  `text_to_timestamptz_immutable`), `idx_health_raw_start_time` (plain lexical,
  used by the summary function's ISO-prefix range trick) and
  `idx_raw_external_id`.
- Idempotency rests on `UNIQUE (source_id, original_type, external_id)` on
  observations and `UNIQUE (source_system, source_name, external_source_id)` on
  sources.

## Open data-quality issues

1. **235,000 rows across 25 metric types are named `HK*`** — raw Apple Health
   identifiers that were never mapped onto the archive's canonical vocabulary
   (e.g. `HKQuantityTypeIdentifierWalkingSpeed`, `HKQuantityTypeIdentifierPhysicalEffort`,
   `HKCategoryTypeIdentifierAppleStandHour`). No dashboard panel will ever match
   them. They need a mapping pass, or an explicit decision to leave them raw.
2. **Blood pressure is already fragmented**: `blood_pressure` (google_fit) vs
   `blood_pressure_systolic`/`blood_pressure_diastolic` (health_connect).
3. **The same measurement arrives from up to six source systems.** `steps`,
   `heart_rate` and `sleep_segment` each have five or six. Any panel that sums
   across sources without precedence will double-count — which is exactly what
   `refresh_health_daily_numeric_summaries` was written to solve.
4. The PVC is ~47% full. A full-table rewrite (e.g. `ALTER COLUMN ... TYPE
   timestamptz`) needs roughly the table size again in free space and would not
   comfortably fit. Prefer additive columns.
